# ARCH 实质审查 profile

Layer 2 审查 `arch` 时按 review.md 路由加载本文件。审查立场: 假设设计存在缺陷并求证——每个维度回答「按此架构实现,何处会返工、何处扛不住 PRD 的要求」,而非确认章节齐全。

## 实质维度

**选型可追溯 (feasibility)**
- 关键选型(存储、通信方式、部署形态、核心依赖)有 ≥2 个真实备选的对比与选择理由;「流行/团队熟悉」单独不构成理由
- 差: 技术栈表只有结论列;好: 每项关键选型附备选、权衡与重评条件

**PRD 覆盖与 NFR 兑现路径 (consistency)**
- 每个 P0 功能可指认承载模块(映射的字面存在性由 Layer 1 一致性机检承载,此处只判兑现质量);每条 NFR 有具体架构机制承接(容量→扩展策略、可用性→故障转移、安全→信任边界),不是复述 PRD 数字
- 差: 「性能: 支持高并发」;好: 「峰值请求量估算 X,由无状态服务水平扩展 + 读缓存承接,瓶颈预计在写路径」

**数据所有权与一致性 (structure)**
- 每类核心数据有唯一 owner 模块;跨模块读写路径明确;并发写与部分失败后的一致性语义(强一致/最终一致/补偿)有声明

**故障面 (error-handling)**
- 单点故障已识别;外部依赖不可用时的降级行为有定义;重试有幂等前提;数据恢复路径(备份/重放)存在
- 差: 「调用第三方接口获取数据」;好: 「第三方超时后降级为缓存快照并标注陈旧,重试仅限幂等读」

**模块边界与依赖方向 (coupling)**
- 依赖方向单向无环;单个模块职责一句话可说清;无「上帝模块」(被所有模块依赖又依赖所有模块)

**过度设计 (feasibility)**
- 架构复杂度与 PRD 规模匹配;每个引入的分布式组件/中间件/缓存层须能指认它兑现的需求条目,指认不出即点名报出
- 差: 单团队小工具套「微服务 + 消息队列 + 多级缓存」全家桶;好: 单体起步并记录触发拆分的重评条件

**接口契约完整性 (consistency)**
- 对外 API 定义错误语义(错误码/异常路径)、幂等性、版本演进策略;实体字段与 PRD 业务规则一致

**安全边界 (security)**
- 认证/授权在架构层有明确位置(哪里校验、哪段可信);密钥与敏感配置的存放与轮换有交代;信任边界跨越处(用户输入、外部回调)有防护声明

## 严重度锚点

| 缺陷 | 起评 |
|------|------|
| 认证/授权位置不明、信任边界无防护 | CRITICAL |
| P0 功能无承载模块、NFR 无兑现机制 | HIGH |
| 核心数据无 owner、一致性语义缺失 | HIGH |
| 关键选型无备选对比、依赖成环 | HIGH |
| 外部依赖无降级定义、单点未识别 | MEDIUM(核心链路升 HIGH) |
